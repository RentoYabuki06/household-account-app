# 015 レシート読み取りのサーバー側（API・合言葉・回数の上限）

## 目的
撮影したレシートの写真から、店名・日付・金額・カテゴリ候補を取り出すサーバー側の処理を作る。読み取りには Gemini（Google AI Studio の無料枠）を使う。画面側は次のノート（016）で作る。

## 変更内容
- `app/api/receipt/route.ts`（新規）: `POST /api/receipt`。合言葉の確認 → 入力の検査 → 1 日の回数の確認 → Gemini の呼び出し → 結果の検査と整形
- `migrations/008_receipt_scan_limit.sql`（新規）と `schema.sql`: 日別の回数のテーブル `receipt_scans`、回数を原子的に数える関数 `consume_receipt_scan`（service_role だけが実行できる）
- `.env.local.example`、`README.md`: 必要な環境変数と手順

## 設計判断
- **Gemini の Interactions API（`/v1beta/interactions`）を使った。** 公式ドキュメントが、従来の `generateContent` ではなくこちらを既定にしている（`generateContent` は「互換のために残るレガシー」とされている）。リクエストの形（`input`、`system_instruction`、`response_format`）と、応答の形（`steps` の `model_output` の `text`）は、公式ページの記載に合わせた。SDK は使わず、`fetch` で呼ぶ。
- **モデルは `gemini-3.5-flash-lite`（安定版）を既定にした。** 画像入力に対応し、料金表で無料枠の対象になっている。環境変数 `GEMINI_MODEL` で変えられる。
- **守りを重ねた。**
  - 合言葉（`x-receipt-passphrase`）。ハッシュを定数時間で比べる。一致しなければ、Gemini も DB も呼ばない。
  - 1 日の回数の上限（既定 30）。Gemini を呼ぶ前に数える。数える処理は、SQL の 1 文で原子的に行う。
  - 指示文はサーバーで固定し、出力は決められた JSON に絞る。画像は 1.5MB、JPEG/PNG/WebP のみ。返答は最大 2048 トークン。
  - 返ってきた内容は検査し直す（金額は 1〜9,999,999 の整数、日付は実在する今日以前、時刻は HH:MM、カテゴリは候補の中から）。
- **「不明」は null にして返す。** 読めなかった項目は、画面で空欄のままにして、利用者が入力する。
- **応答のスキーマに `nullable` を使わなかった。** ドキュメントで確認できなかったため、空文字と 0 を「読めない」の印にした。
- 回数の記録には、Supabase の secret key をサーバー側（Vercel の環境変数）に置く。ブラウザには出ない。

## 動作確認
- `next build` が通ることを確認した。
- 偽の Gemini・偽の Supabase を手元で立てて、`next dev` の `/api/receipt` に 10 パターンを送った。
  - 合言葉なし・違いは 401、画像なし・PDF は 400、大きすぎは 413
  - 正常な呼び出しで、金額（3170.4 → 3170）と店名の整形、候補外のカテゴリが null になること
  - Gemini が 429 のときは 503、レシートでないときは 422
  - 上限を 4 回にして、5 回目が 429 になること（上限を超えた呼び出しは Gemini に届かない）
  - Gemini が受け取った内容（API キー、`Api-Revision`、モデル、システム指示、画像の形式、カテゴリの候補）
- **未確認（重要）:** 本物の Gemini との通信。偽のサーバーは、私がドキュメントから読み取った応答の形で作ったので、実際の応答がそれと違えば動かない。特に次の点は、公式ページに記載がなく、実機で確かめる必要がある。
  - ブロックされた応答や空の応答の形
  - `max_output_tokens` に思考の分が含まれるか
  - 無料枠の1日の回数と、日本からの利用可否
  - 画像からの実際の読み取り精度

## 注意点・残課題
- Vercel に環境変数を入れ、Supabase で `008_receipt_scan_limit.sql` を実行するまで、読み取りは 503（未設定）を返す。
- 無料枠では、送った内容が Google の製品改善に使われる。
- 合言葉の総当たりへの対策は、長いランダムな文字列に頼っている。失敗回数の制限は設けていない。
